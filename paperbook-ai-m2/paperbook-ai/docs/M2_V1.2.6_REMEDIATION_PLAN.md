## 1. 三项问题与根因

### P0-01 混合安全字段仍可能错误放行

原始缺陷：`safety` 里出现未知字段（如 `score`）、`flags: null`、或 `pass` 与 `flags` 互相矛盾时，解析层会“取自己认识的部分”继续判断，未知风险未被记录。

根因：

1. `parse_safety` 只读取 `pass`/`flags`，多余键被静默忽略（`src/vision/safety.py`）。
2. `flags: null` 与 `flags` 缺失共用同一条 `safety_flags_missing`，语义被压平。
3. 后端结果与原始 `safety_raw` 的一致性只在部分字段比较，`flags` 被“原因串”替换过（V1.2.1 旧路径）。

整改：

- `_ALLOWED_SAFETY_KEYS = {"pass", "flags"}`；任何额外键 → `safety_unknown_field:<key>`。
- `flags: null` → `safety_flags_null`（缺失仍是 `safety_flags_missing`）。
- `evaluate_vlm_safety` 重新解析 `safety_raw`，逐字段对照后端结果；不一致 → `safety_flags_mismatch` / `safety_pass_mismatch` / `safety_evidence_mismatch`。
- 任一条原因 → 3004，不写 C2、不写 sidecar、不返回 `code=0`。

### P0-02 安全拦截后旧索引仍可能被加载

原始缺陷：`scripts/build_masks.py`、`enrich_index.py`、`tap_demo.py`、`examples/consume_tap.py` 直接 `index.load()`；`index.load()` 自身不校验安全，安全门禁只发生在更早的 `build_from_vlm`。因此磁盘上存在历史索引时，绕开构建阶段即可消费旧资产。

根因：索引读取与安全判定是两条独立路径；`load()` 没有“安全凭证”概念。

整改：

- `safety.SafetyClearance` + `issue_clearance()` + `clearance_for_document()`。
- `index.load(data_dir, page_id, *, clearance)`：无凭证/类型非法/页不匹配一律拒绝，之后才严格解析索引文件。
- `index.load_after_gate()`：先读 C2 → 严格解析 → 页校验 → 安全复检 → 签发凭证 → 读索引；`SafetyBlocked` 统一转成 `UnsafeIndexError`。
- 四个脚本/示例全部改用 `load_after_gate`；`scripts/build_index.py` 的“保留旧讲解”分支也先复检再读旧索引。

### P1-01 `clothing=null` 与 M1 Gate 不兼容

根因：sidecar 的 `appearance.clothing` 被固定写成 `None`，而 M1 Gate 当前不接受 `null`。

整改（字段映射方案，待 M1 确认）：

| 场景 | M2 输出 | 说明 |
|---|---|---|
| 未识别到服装 | **省略 `clothing` 键**（默认） | 缺省 = 未知，不是伪造的空字符串 |
| 识别到服装 | `"clothing": "蓝色外套"` | 字符串，长度受限 |
| 显式要求 null | `"clothing": null`（`M2_SIDECAR_CLOTHING=null`） | 仅供 M1 后续支持时使用 |

不把 `null` 自动转成 `""`，也不新增字段绕开 Gate。
