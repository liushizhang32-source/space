### 新 P2 的独立复现及可达边界

只在RAM中建立与源码一致的表，设置RLock/固定时钟、真实Core对象和真实FakeProvider对象，不修改源码、不覆写业务方法，不调用provider网络。实际调用序列：

1. 配预算，创建页03的Job A，持有其当前identity。
2. `c.submit(identity, provider, fault=before)`：在 `intent_before_dispatch` 抛 RuntimeError；捕获后断言 state=not_submitted、resource=None、provider.calls=0。
3. 再次 `c.submit(identity, provider, fault=after)`：在 `provider_after_submit_before_record` 抛 RuntimeError；收到 submit_unknown，断言 state=unknown、resource=None、backend_terminal_confirmed=0、provider.calls=1、unresolved(A)=True。
4. 创建页04的Job B，调用其 `c.submit`，成功，provider.calls=2。此时A仍为unknown/NULL/未确认，B为confirmed/NULL/已确认。

探针实际stdout：

```text
PROBE pre-dispatch failure: not_submitted None 0
PROBE retry exception: submit_unknown; reconciliation required
PROBE uncertain retry: unknown None 1 unresolved= True
PROBE other-job submit allowed while first unknown: [('unknown', None, 0), ('confirmed', None, 1)] calls= 2
PROBE no-dispatch release + transaction rollback + replay: PASS
```

这是已公开使用并由原46项中的并发submit测试直接调用的Core.submit接口路径。常规runner会在第一次普通异常后将Job失败，因而**本轮未证明正常runner会自动触发这次重投**。但Core没有禁止这个可重入分支，无法保证“所有unknown都保留共享租约”。FakeProvider本身即时终止，探针不声称真实服务器并发执行或真实费用损失；证明的是本地状态机丢失资源占用，且能绕过共享resource唯一约束。建议在Core边界修复，不能仅依赖调用者碰巧失败Job。
