## 7. F05：Prompt Hash 与来源真实性

### 7.1 Prompt Hash

采用确定性消息序列化。

Hash 对象为：

实际提交给 Provider Adapter 的最终有序消息列表。

必须包含：

- 每条消息的 role。
- 每条消息的最终 content。
- 消息顺序。
- 所有模板替换结果。
- 实际使用的文本参数。

采用确定性 JSON 序列化：

- UTF-8。
- 无 BOM。
- 无额外空白。
- 固定字段顺序或 RFC 8785 JCS。
- 不允许 NaN/Infinity。
- 不允许无效 Unicode。
- 不允许擅自 trim。
- 不允许修改消息顺序。

对规范化后的最终字节计算 SHA256。

必须区分：

- Prompt Template Hash。
- Final Prompt Hash。
- Provider Request Hash。

本协议的 prompt_sha256 指 Final Prompt Hash。

不包含 API Key、Token、Secret。

图片和其他二进制附件必须分别计算原始字节 SHA256，并记录与对应消息的关联。

不得将模板文件 Hash 冒充最终 Prompt Hash。

不得宣称该 Hash 证明 Provider 内部未修改消息。

Hash 的证明范围是应用提交给 Provider Adapter 的精确消息内容。

如果 SDK 在后续阶段进行了不可观察的转换，必须如实说明 Hash 的边界。

### 7.2 来源模式

合法枚举：

- fixture
- stub
- real

本次离线联调只允许：

fixture、stub。

real 不在本次执行授权范围内。

component_mode=real 只是来源声明，不是实际供应商执行证明。

必须区分：

- 声明来源。

## 10. F08：错误码、状态与持久化重试

### 10.1 每 Stage 最多两次总尝试

正式规则：

每个逻辑 Stage 最多两次总 Attempt：

- Attempt 1：首次执行。
- Attempt 2：最多一次重试。

适用范围：

每个独立的 job/page/generation/revision/epoch/stage 工作单元。

OCR 和 VLM 分别计算次数。

### 10.2 持久化要求

Attempt 计数必须由 M1 权威管理。

必须：

1. 在提交前持久化 Attempt 记录。
2. 为每次 Attempt 生成唯一 attempt_id。
3. 为每次 Attempt 生成唯一 fencing_token。
4. 跨进程重启保持计数。
5. 跨 Supervisor 重启保持计数。
6. 防止重复入口绕过次数上限。
7. 防止并发提交重复占用 Attempt。
8. 对提交结果 unknown 的情况保留已消耗的 Attempt 记录。

M2 不得自行维护权威重试次数。

M2 不得执行 SDK 隐式重试。

M2 每次只执行 M1 指派的一次 Stage。

如果当前 M1 尚未具备跨进程持久化计数能力，必须列入 M1 实现缺口，不得假称已实现。

### 10.3 重试条件

9001：
不重试。

3004：
安全拦截，不重试。

3001：
保留原有合法 OCR empty 特殊处理，不将其当作普通错误重试。

2004：
必须区分 typed cancellation 和 transient error envelope。

typed cancellation：
不重试。

transient error envelope：
只有对应精确子类型或错误标识明确存在于 M1 retry allowlist 时，才允许重试。

timeout：
必须先取得可信终止确认，才允许考虑重试。

cancellation：
不自动重试。

unknown：
保留资源租约，等待对账；禁止自动重投。
